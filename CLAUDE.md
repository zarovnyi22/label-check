# Label Check — правила проєкту для Claude Code

Тестова таска: R&D-відділ харчового виробника. Перед запуском кожного продукту технолог
вручну звіряє упаковку: чи правильно вказані алергени і чи не порушують закон написи на
кшталт «без цукру» чи «джерело білка». Година роботи на продукт; помилка = відкликання
партії. Сервіс за фото упаковки робить цю перевірку замість технолога.

Обмеження: Python, FastAPI, PostgreSQL, Docker; лише безкоштовні сервіси без картки;
8 годин. Що здати: репозиторій, що запускається з нуля за README; **число, яке показує,
наскільки сервісу можна довіряти, і як його отримано**; коротко — рішення, жертви, що далі.

Деталі (пороги, словник, схема БД, eval) — `docs/SPEC.md`, читати лише розділ, потрібний
кроку; «чому так» — `docs/OVERVIEW.md`; промпти кроків — `docs/PROMPTS.md`.

Головне правило роботи: Claude пише код, людина тримає архітектуру і перевіряє кожен блок
руками (curl і очима, а не «повірити на слово»). На співбесіді питатимуть «чому так».

## Рішення і припущення (записані в першу годину)

1. **Ринок — Україна, мова етикетки — українська** (відповідь PM); англійські дублікати на
   упаковці теж розпізнаються. Правова база:
   - Закон України № 2639-VIII «Про інформацію для споживачів щодо харчових продуктів»
     (гармонізований з Регламентом ЄС 1169/2011): 14 алергенів; алергени у складі
     **виділяються шрифтом** (жирний, великі літери, підкреслення, колір).
   - Наказ МОЗ № 1145 від 15.05.2020 «Вимоги до тверджень про поживну цінність та про
     користь для здоров'я», обов'язковий для всього маркування з 21.08.2023 (відтворює
     додаток Регламенту ЄС 1924/2006). Пороги в `app/rules/claims.py`; кожне правило має
     `legal_ref`.
2. **Еталон для алергенів — рецептура (специфікація)** (рішення наше за дорученням PM).
   Повноцінний, але необов'язковий вхід:
   - зі специфікацією — закон + відповідність етикетки рецептурі;
   - без специфікації — закон і внутрішня узгодженість; повноту алергенів сервіс не
     стверджує: `not_checked` «без рецептури не перевірити», загальний вердикт не `pass`.
3. **Пропущене порушення гірше за хибну тривогу** (відкликання партії проти зайвої
   хвилини технолога). Сумнів → `needs_review`, ніколи `pass`. Але сервіс, що все віддає
   людині, нічого не економить, тому навантаження на людину міряємо поруч із recall.
4. **До 4 фото в одному запиті, один виклик моделі на запит** (всі фото разом): твердження
   зазвичай спереду, склад і нутрієнти ззаду.
5. Лише **твердження про поживну цінність** (≈ 13). Твердження про користь для здоров'я,
   порівняльні («на 30 % менше», «легкий») і нерегульовані («натуральний», «корисний») →
   `needs_review` з поясненням, не автоматичний вердикт.
6. Фронтенду немає — демо через Swagger UI (`/docs`).
7. **Моделі** (B0, перевірено в AI Studio і Groq 01.10.2026):
   - основна — `VISION_MODEL=gemini-3.5-flash-lite` (free tier: 15 RPM, 250K TPM, 500 RPD;
     `gemini-2.5-flash` не беремо — лише 20 RPD);
   - запасна — Groq `qwen/qwen3.8-27b` (`GROQ_VISION_MODEL`; єдина vision-модель на Groq,
     ≤ 3 фото на запит, ≈ 2048 токенів на фото) — лише для запитів з ≤ 3 фото; 4 фото +
     основна недоступна → `vision_rate_limited`. `VISION_FALLBACK_PROVIDER` за
     замовчуванням порожній; сам fallback — у B3a;
   - число довіри міряється лише на основній моделі; пауза між запитами eval ≥ 5 с.

## Архітектура: модель читає, код вирішує

```
фото (1–4) → підготовка (тип/розмір, EXIF-поворот, ≤ 2048 px, sha256)
          → vision-LLM: ЛИШЕ транскрипція в JSON (LabelExtraction), без суджень,
            числа — рядками як на фото, виділення — markdown-розміткою
          → кеш екстракції: sha256 фото + PROMPT_VERSION + модель (eval без LLM)
          → код: розбір чисел і розмітки → нормалізовані факти (app/parsing.py)
          → правила в коді (чисті функції, кожна з legal_ref)
          → findings[] (pass / violation / needs_review / not_checked / not_applicable)
          → verdict: fail > needs_review > incomplete > pass
          → PostgreSQL: фото (байти), сира відповідь моделі, екстракція, findings,
            RULES_VERSION, PROMPT_VERSION, модель, токени, тривалість (аудит)
```

Модель **ніколи** не вирішує, чи є порушення, і не пише тексти findings: вона переносить
текст з фото в структуру. Пороги, арифметика, розбір чисел, словник алергенів, пошук
тверджень, повідомлення і посилання на закон — у коді й покриті тестами.

| Vision-LLM | Gemini (Google AI Studio, free tier), REST через `httpx`, без SDK; модель — `VISION_MODEL` | читає зображення, JSON-режим, без картки |
| Зображення | Pillow (EXIF, resize, hash; генератор синтетичних етикеток) | легко, без браузера |

| CI | GitHub Actions: ruff + pytest, docker build | дешево, скопійовано з `pet` |

Groq `qwen/qwen3.8-27b`, знайдений у B0 (див. «Рішення», п. 7).

## Жорсткі правила (не порушувати)

- **Модель лише транскрибує.** У промпті екстракції — заборона оцінювати законність,
  вигадувати нечитабельне (→ `null`), «виправляти» чи перекладати текст. Вердикти й тексти
  повідомлень — тільки код. Числа в `message` і `evidence` — лише ті, що порахував код.
- **Числа з фото — рядками, розбирає код.** Модель повертає `"<0,5"`, `"3,1"`, `"сліди"`
  як на фото; `parse_amount` у коді дає `{value, qualifier: "lt"|"eq"|"trace"}`. Кома —
  десятковий роздільник. Нерозбірне → `null` → `needs_review`.
- **Виділення — markdown-розміткою в тексті складу** (`сухе **молоко**`), не булевими
  прапорцями по сегментах. ВЕЛИКІ ЛІТЕРИ визначає код. Алерген у `**…**` або ВЕЛИКИМИ →
  `ALG-EMPH` `pass`; без виділення → **лише `needs_review`** («модель не підтвердила
  виділення алергену»), ніколи `violation`: проба B1b показала, що модель пропускає жирний
  шрифт (p17: 0 з 6), тож відсутність `**` — не доказ порушення. `emphasis_resolvable`
  (чи дозволяє фото розрізнити шрифт) лише уточнює пояснення. Точніше виділення — кандидат B6.
- **Межі складу код не довіряє:** текст від «Зберігати»/«Умови зберігання»/«Виробник»/«Може
  містити»/«ДСТУ»… відрізається (`parse_ingredients` → `tail`) — алергени там не шукаються.
- **Обрізане/нечитабельне — маркер `[…]`** на його місці, ніколи не дописувати й не
  пропускати мовчки; `[…]` у складі → `LABEL-TRUNCATED` = `needs_review`. `quality` від
  моделі — лише підказка.
- **Твердження шукає код**, а не модель: модель транскрибує весь текст упаковки поза складом
  і таблицею (`other_text`), правила знаходять твердження регулярками (uk + en).
- **«Невідомо ≠ можна».** Нечитабельне поле, погане фото, відсутній бік упаковки, таблиця
  лише на порцію, немає рецептури → `needs_review` або `not_checked`, ніколи `pass`.
  `pass` загалом — лише якщо всі застосовні перевірки `pass` і немає `not_checked`.
- **Фікстури і кейси генеруються, а не пишуться руками.** Тести правил беруть екстракції з
  `truth.json` синтетики (той самий генератор, що й eval). Ручна фікстура ховає баги (урок `pet`).
- **Тести ніколи не ходять у живий LLM і мережу.** Лише `FakeVision`; сервіс `test` у
  compose — в ізольованій мережі, ключі порожні (як у `pet`).
- **Eval чесний:** набір ділиться на `dev` і `test`. Промпт, словники й пороги
  налаштовуються лише на `dev`; **число довіри — тільки з `test`**, один раз, після нього не
  доналаштовують. Синтетичні дані позначаються як синтетичні.
- **Помилки:** `{"error": {"code": "...", "message": "..."}}`. Коди vision:
  `vision_not_configured`, `vision_invalid_key` (не ретраїться), `vision_rate_limited`,
  `vision_unavailable`, `vision_timeout`, `vision_bad_output` (невалідний JSON після одного
  повтору); фото: `image_too_large`, `image_unsupported`, `too_many_images` (422: > 4 фото
  або > 3 при `VISION_PROVIDER=groq`).
- **Повтори** на 500/502/503/504/таймаут: 2, 4, 8 с + джиттер, повтор починається лише в
  межах 60 с; одна спроба ≤ `VISION_TIMEOUT_SECONDS` (45). 429 — без повторів у межах запиту
  (або запасний провайдер, якщо є). Загальний дедлайн `run_check` —
  `VISION_DEADLINE_SECONDS` (120) → 504 `vision_timeout`, перевірка в БД зі `status=error`.
- **Міграції** нумеровані й ідемпотентні; застосовані не редагуються.
- **Секрети** лише в `.env` (у `.gitignore`); `.env.example` — назви з коментарями.
- **Один крок плану (B1b, B2a…) = один коміт**, наступні кроки наперед не робимо.

## Автономний режим (як виконувати крок)

Людина пише «Виконай крок <X>». Тоді:
1. Прочитай `docs/steps/<X>.md`, розділи SPEC/NOTES, на які він посилається, — і більше
   нічого без потреби (OVERVIEW — лише якщо треба «чому»; `~/pet` — лише названі файли).
2. Зроби крок. Ворота з файлу кроку запускаєш **сам**. Червоне — виправ; після 3 невдалих
   спроб на тому самому — зупинись і опиши проблему.
3. Самоперевірка за `docs/steps/REVIEW.md`: критичне й важливе виправ (з тестом), ворота
   ще раз; дрібниці — у звіт.
4. Онови «Статус кроків», `docs/NOTES.md` (висновки, відкриті питання), закоміть з
   повідомленням із файлу кроку і `git push`.
5. Звіт ≤ 15 рядків: що зроблено; ворота; що знайшла самоперевірка; відкриті питання;
   наступний крок.

**Зупинись і спитай людину**, якщо: потрібне рішення поза планом (зміна архітектури, схеми
БД, правила з CLAUDE.md); ворота червоні після 3 спроб; живих викликів LLM більше за
бюджет кроку; позначка ⏸ у файлі кроку.
**Ніколи:** `--no-verify`, `push --force`, редагувати застосовані міграції, відкривати
`samples/test/` чи `eval/real/` в основному контексті (лише субагент у B4b і eval-раннер),
доналаштовувати щось після фінального заміру на test.

## Контракти (коротко; повністю — `docs/SPEC.md` §1)

- `POST /checks` (multipart: `images` 1–4, `spec` — необов'язковий JSON `ProductSpec`),
  `GET /checks/{id}`, `GET /rules`, `GET /health`.
- `LabelExtraction` — лише транскрипція: `photos[{index, side, quality}]`,
  `emphasis_resolvable`, `ingredients_marked` (склад з `**…**`, `[…]`), `may_contain_text`,
  `nutrition` (рядки як на фото + `per`), `other_text[]`; усе з `photo_index`, усе може
  бути `null`.
- `finding = {rule_id, target, status, message, evidence, legal_ref}`; статуси
  `pass | violation | needs_review | not_checked | not_applicable`.
- `verdict`: `fail` > `needs_review` > `incomplete` (є `not_checked`) > `pass`.

## Правила (перелік; пороги, словник і деталі — `docs/SPEC.md` §2)

- Загальні: `IMG-QUALITY`, `LABEL-MISSING`, `LABEL-TRUNCATED`, `SIDE-FRONT-MISSING`,
  `NUT-PER`.
- Алергени: `ALG-EMPH`, `ALG-SPEC-MISSING`, `ALG-SPEC-EXTRA`, `ALG-MAY-CONTAIN`.
- Твердження: 13 id (`sugar_free`, `protein_source`…) + `CLAIM-UNVERIFIABLE`.
- Узгодженість: `NUT-ENERGY`, `NUT-KJ`, `NUT-SUBSETS`, `NUT-SPEC`.

## Число довіри (коротко; повністю — `docs/SPEC.md` §4)

Порушення зараховується лише за `{rule_id, target}`. Головне число — safe recall
(`violation` або `needs_review`) з 95 % інтервалом Вілсона **разом із** навантаженням на
людину і базовою лінією «все → needs_review». Налаштовуємо на `dev`, міряємо `test` один раз.
