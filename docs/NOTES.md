## B1b — проба моделі

`gemini-3.5-flash-lite`, 2 виклики (p02: 3 фото; p03: 2 фото), фото ≤ 2048 px, temperature 0,
`responseMimeType: application/json`, чорновий промпт у `scripts/spike_vision.py`.
- **Добре:** кирилиця читається; таблиця нутрієнтів точно, рядками з комою («0,2 г/g»,

  фронтові написи (зокрема твердження «З НАТУРАЛЬНИМИ ІНГРЕДІЄНТАМИ*») — в `other_text`;
  `side` правильний; JSON валідний з першого разу.
- **Погано 1 — домислює обрізане:** p02 «прянощі … (оріган, …)» — «оріган» на фото немає
  (там кориця/лавровий лист, обрізано); p03 дописала обрізані «діоксид вуглецю»,

- **Погано 2 — `quality: ok`** на обох обрізаних фото звороту: на `quality` моделі
  `IMG-QUALITY` спиратися не можна.
- **Погано 3 — виділення не бачить:** p02 `emphasis_visible: false`, хоча алергени в «Може
  містити …» помітно жирніші. За правилом це безпечно (`ALG-EMPH` → `needs_review`), але на

  поживна цінність надрукована текстом, а не таблицею, дублює її в `other_text`.
- **Токени/час:** ≈ 1070 токенів на фото 2048 px, ≈ 650 промпт, 1100–1300 вихід →

**Проба 2 — склади з алергенами** (p16 вафлі Roshetto, жирний курсив; p17 шоколад Milka,

## B2a — схеми і розбір

- `parse_amount` → `Amount(value у грамах, eq|lt|trace)`; `trace` має `value=None` навмисно
  (жодне правило не порівняє «сліди» як число); «≤» теж `lt` (верхня межа). Decimal, тож
  «0,1 мг» == 0.0001 і «0,5» == літерал 0.5 — пороги порівнювати прямо (`<=`); допуск
  потрібен лише для арифметики (NUT-ENERGY, % енергії) — B2c.
- `parse_energy` → `Energy(kj, kcal)`; дві різні колонки в одному рядку або «<» → `None`.
- `parse_ingredients` → `Ingredients(mentions, tail, truncated, upper_is_body,
  marks_are_body)` (не голий список, як у SPEC: B2b потрібні межа і прапорці).
  `Mention(text, emphasized_spans, upper, depth).is_emphasized(start, end)`. Межа складу:
  від «Зберігати / Умови зберігання / Виробник / Може містити / Може вміщувати / Поживна
  цінність / ДСТУ…» — `tail`, не склад (p17: зберігання й виробник відрізано). **B2b:** якщо
  `may_contain_text` null, а в `tail` є «Може містити…», брати звідти. Весь склад ВЕЛИКИМИ /
  весь у `**` (> половини слів) — стиль тексту, spans скидаються. Непарний останній `**`
  ігнорується (без виділення — безпечне читання). Речення («ароматизатор. Мінімальний…»)
  ділять згадки, нічого не відрізаючи.
- Реальний вивід проби (4 відповіді моделі дослівно) — `tests/spike_outputs.py`; ним
  перевіряються схеми й розбір. B2b може брати склади звідти.
- `ProductSpec` і вкладені — `extra="forbid"` (одруківка в `allergens` не стає «без
  алергенів»); `LabelExtraction` — невідомі ключі відкидаються, невідомі значення enum →
  `null` (`side` → `unknown`), числа від моделі → рядки.
- Категорії алергенів (`AllergenCategory`, `app/schemas.py`): cereals, crustaceans, eggs, fish,
  peanuts, soybeans, milk, nuts, celery, mustard, sesame, sulphites, lupin, molluscs.

## B2b — алергени

- `check_allergens(extraction, spec) -> list[Finding]` (`app/rules/allergens.py`) — для
  рушія B2c. Одна finding на категорію (`target`); `pass`/`not_checked`/`not_applicable`
  без категорії мають `target: null`. Порядок категорій — як у `AllergenCategory`.
- ALG-EMPH: згадка зараховується виділеною і тоді, коли одразу за нею вкладена згадка того
  самого алергену виділена — «сироватковий пермеат (з **молока**)» (p16). Без складу
  ALG-EMPH не видає нічого (це LABEL-MISSING, B2c); склад без алергенів → `not_applicable`.
- ALG-SPEC-MISSING: склад не прочитано або є `[…]` → `needs_review`, не `violation`;
  алерген лише в «може містити» не зараховується як наявний у складі.
- ALG-MAY-CONTAIN: якщо `may_contain_text` null — речення з `tail` складу.
- На пробі: p16 — cereals/soybeans pass, milk needs_review («молоко сухе незбиране», яке
  модель пропустила); p17 — milk/nuts/soybeans needs_review (0 з 6 жирних розпізнано);
  p02 «мускатний горіх» і p03 «сульфітно-аміачна карамель» — не алергени.
- Відома межа словника (кандидат для dev-тюнінгу в B4/B5): речення після складу без
  маркера («Мінімум 25 % молочних продуктів…», p17) лишається згадкою і може дати зайвий
  needs_review або «знайти» алерген. «Горіх земляний» → peanuts і кедровий горіх → не
  алерген — виправлено (fix(b2b)).
- Статті Закону 2639-VIII у `catalog.py` не звірені (TODO); статті Регл. 1169/2011 — точні.

## B2c — твердження, нутрієнти, рушій

- `run_rules(extraction, spec) -> (findings, verdict)` (`app/rules/engine.py`),
  `RULES_VERSION = "2026-10-01.3"` (піднімати при зміні правил/порогів/словників).
  Порядок findings: загальні, алергени, твердження, нутрієнти. `GET /rules` — 27 правил.
- Твердження: `rule_id` = `target` = id твердження (`sugar_free`), як у CLAUDE.md.
  CLAIM-UNVERIFIABLE: `target` = вид (`comparative` / `health` / `unregulated` /
  `nutrition_other`), одна finding на вид. Шукаються лише в `other_text`.
- Числа з `lt`: діапазон [0, v] — pass, якщо весь діапазон проходить, violation, якщо весь
  не проходить, інакше needs_review («<1 г» для «без цукру»). `lt` = і «<», і «≤», тому
  «<3 г» білка при 100 ккал — needs_review, не violation. «Сліди» у твердженнях →
  needs_review; лише в NUT-ENERGY беруться як [0; 0,5 г] (`TRACE_MAX_G`).
- `fmt()` — числа в повідомленнях з комою; частки енергії порівнюються через `at_least`
  (`math.isclose`), щоб 3 г білка / 100 ккал = рівно 12 % давало pass.
- `no_added_sugar`: цукри/мед/сиропи/декстроза/глюкоза/фруктоза/сахароза/мальтоза/лактоза/
  патока/концентрований сік у складі → violation; мальтодекстрин → needs_review «спірний
  підсолоджувальний інгредієнт» (але violation з інших причин переважає); цукри > 0,5 г без
  «містить природні цукри» → violation; склад з `[…]` → needs_review.
- Форма (тверде/рідке): `spec.form`, інакше з `per` (100g/100ml); невідома, а пороги різні →
  needs_review.
- IMG-QUALITY дає лише needs_review для поганих фото; «ok» не дає pass (і finding немає).
- SIDE-FRONT-MISSING → `not_checked`, але твердження з наявних фото все одно перевіряються.
- Чистий продукт без рецептури → `incomplete` (повнота алергенів), з рецептурою → `pass`.

## B5a — eval-раннер

- `eval/run.py` (`make eval SPLIT=… [LIMIT=N]` — лише кеш; `make eval-live …` — модель для
  відсутніх, пауза `EVAL_PAUSE_SECONDS`=5 с): кейси через `app.checks.run_check` без HTTP.
  Групи: dev — synthetic; test — synthetic, `real` (без рецептури), `semi` (той самий кейс
  з кожною spec_variant — екстракція одна, з кешу), `out_of_scope` (`in_trust_number:
  false`). Без `--live` і без кешу — помилка зі списком кейсів, нічого не запускається;
  кейс без фото (справжні фото не в git) — теж у списку. Помилка моделі → `status: error`,
  не кешується, наступний прогін повторює лише її. Звіт `eval/reports/<split>_<дата>.json`:
  model, prompt/rules version, по кожному unit — violations, expected_flags, meta (oov,
  ambiguous, quality), findings (rule_id/target/status), verdict, **extraction** (для
  точності читання в B5b), cache_hit, usage, duration.
- Число довіри — лише основна модель: раннер вимикає `VISION_FALLBACK_PROVIDER`.
- Сервіс `tools` тепер має `DATABASE_URL` на `db` і `depends_on: db` (кеш екстракцій у
  Postgres, як в api).
- Ворота: `make eval-live SPLIT=dev LIMIT=3` — 3 живі виклики, 0 помилок (dev-001 `fail`,
  dev-002/003 `needs_review`); `make eval SPLIT=dev LIMIT=3` — усі з кешу; LIMIT=4 без
  кешу → зрозуміла помилка «dev-004». Пробний звіт на 3 кейси не комічу (B5b перезапише).
  Спостереження: dev-001 `fail` — хибний ALG-SPEC-MISSING через oov «рікота» (так і
  задумано: oov міряє покриття словника).
- **Відкрите:** кеш екстракцій живе в Postgres, а не в git → на чистому клоні `make eval`
  без `--live` не відтворить число; варіант — експорт кешу в `eval/cache/*.json` (B7?).
