# Label Check — огляд таски, рішення, архітектура і логіка

Документ збирає все, що вирішено до початку кодування: умову, питання до PM і прийняті
рішення, архітектуру, логіку перевірки, спосіб виміряти довіру і план на 8 годин — і
**чому** саме так. Правила для Claude Code (стисло, як закон) — у `CLAUDE.md`, покрокові
промпти — у `docs/PROMPTS.md`.

---

## 1. Умова таски

Ми R&D-відділ харчового виробника. Перед запуском кожного продукту технолог вручну звіряє
упаковку: чи правильно вказані алергени і чи не порушують закон написи на кшталт «без
цукру» чи «джерело білка». Це година роботи на продукт, а помилка означає відкликання
партії.

**Зробити сервіс, який за фото упаковки робить цю перевірку замість технолога.**

Обмеження: Python, FastAPI, PostgreSQL, Docker; лише безкоштовні сервіси без картки;
8 годин; працювати з Claude можна і треба; у першу годину — не більше двох питань, далі
рішення за нами, припущення записуємо.

Що здати: репозиторій, який запускається з нуля за README; **число, яке показує, наскільки
сервісу можна довіряти, і як його отримано**; коротко — рішення, жертви, що далі.

## 2. Питання до PM і прийняті рішення

Два питання, які визначають архітектуру (не деталі):

1. **Що є еталоном для алергенів** — чи разом із фото є рецептура/специфікація продукту,
   чи етикетку треба перевіряти лише саму із собою і з законом?
2. **Який ринок і мова етикетки** — і що гірше: пропущене порушення чи хибна тривога?

| # | Рішення | Обґрунтування |
|---|---|---|
| 1 | **Ринок — Україна**, мова етикетки українська (англійські дублікати теж читаються) | відповідь PM |
| 2 | **Рецептура — повноцінний, але необов'язковий вхід** | справжня робота технолога — звірити етикетку із затвердженою рецептурою; найнебезпечніша помилка («в продукті є молоко, а на етикетці немає») з самого фото не видна. Без рецептури сервіс перевіряє закон і внутрішню узгодженість, а повноту алергенів чесно позначає `not_checked` |
| 3 | **Пропущене порушення гірше за хибну тривогу** | відкликання партії проти зайвої хвилини технолога. Сумнів → `needs_review`, ніколи `pass`. Але навантаження на людину міряємо: сервіс, що все віддає людині, нічого не економить |
| 4 | **До 4 фото в одному запиті, один виклик моделі** | твердження зазвичай спереду, склад і таблиця ззаду; один виклик — менше витрат ліміту |
| 5 | **Лише твердження про поживну цінність** (≈ 13) | здоров'я, порівняльні («на 30 % менше», «легкий») і нерегульовані («натуральний») → `needs_review` |
| 6 | **Без фронтенду** — Swagger UI | 8 годин; бекендна таска |

Правова база (Україна):
- **Закон України № 2639-VIII** «Про інформацію для споживачів щодо харчових продуктів»
  (гармонізований з Регламентом ЄС 1169/2011): 14 алергенів; алергени у складі
  **виділяються шрифтом**.
- **Наказ МОЗ № 1145 від 15.05.2020** — вимоги до тверджень про поживну цінність і про
  користь для здоров'я; обов'язковий для всього маркування з **21.08.2023** (відтворює
  додаток Регламенту ЄС 1924/2006). Пороги в коді звірити з текстом наказу; розбіжності —
  у README.

## 3. Головна ідея: модель читає, код вирішує

AI потрібен лише для одного — перенести фото в структуровані дані. Вирішувати, чи є
порушення, має код: пороги, арифметика, словник алергенів і посилання на закон
детерміновані, покриті тестами і пояснювані. Модель може помилитися в порогах, «округлити»
закон чи вигадати цифру; код — ні.

Цей принцип доведено **до кінця** — модель не робить навіть «маленьких» суджень:

| Спокуса | Чому погано | Як робимо |
|---|---|---|
| модель повертає числа (`"sugars": 3.1`) | «3,1» → 31, «<0,5» → 0.5 або null; хибне порушення «без цукру» | модель повертає рядок як на фото, код розбирає кому, «<», «сліди» |
| модель ставить `emphasized: true/false` по сегментах | булеві прапорці по сегментах моделі вгадують; виділяють слово, а не сегмент | модель переписує склад з `**…**` (моделі добре роблять markdown), код знаходить алерген і перевіряє, чи він у `**…**` або ВЕЛИКИМИ |
| модель повертає список тверджень | пропущене твердження = пропущене порушення без сліду | модель переписує **весь** текст упаковки, твердження знаходить код регулярками |
| модель пише пояснення до findings | у `pet` модель писала хибні числа у warnings і назви російською | тексти і числа findings — лише з коду |

Це той самий урок, що в `pet` (Reformulation Assistant): модель обирає/читає, код рахує і
перевіряє — і там, де моделі лишили «трохи» суджень, ПМ знайшов баги.

## 4. Архітектура

```
  Технолог
     │  POST /checks: 1–4 фото + (необов'язково) рецептура JSON
     ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. ПРИЙОМ ФОТО (app/images.py)                               │
│    тип/розмір → поворот за EXIF → ≤ 2048 px → sha256          │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. ЕКСТРАКЦІЯ (app/extraction.py + app/vision/)              │
│    кеш (sha256 фото + версія промпта + модель)? → беремо     │
│    немає → Gemini, ОДИН виклик на всі фото → LabelExtraction │
│    модель ЛИШЕ переписує: склад з **виділенням**, таблицю    │
│    рядками як на фото, весь інший текст. Нечитабельне → null │
│    невалідний JSON → один повтор з текстом помилки           │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. РОЗБІР (app/parsing.py) — код                              │
│    "<0,5" → {0.5, lt}; "**молоко** сухе" → спани виділення   │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. ПРАВИЛА (app/rules/) — чистий Python, без LLM і мережі    │
│    загальні │ алергени │ твердження │ узгодженість нутрієнтів│
│    finding: rule_id + target + статус + evidence + закон     │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────┐
│ 5. ВЕРДИКТ: fail > needs_review > incomplete > pass          │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────┐
│ 6. АУДИТ (PostgreSQL): байти фото, сира відповідь моделі,    │
│    екстракція, findings, RULES_VERSION, PROMPT_VERSION,      │
│    модель, токени, час                                       │
└─────────────────────────────────────────────────────────────┘
```

Кроки 1–5 живуть в одній функції `run_check(images, spec)` (`app/checks.py`). Її викликає і
`POST /checks`, і eval — тож число довіри міряє **той самий код**, що працює в API.

### Стек

| Шар | Вибір | Чому |
|---|---|---|
| Мова, пакети | Python 3.12, `uv`, закріплені версії | як у `pet`, відтворюваність |
| API | FastAPI, Pydantic v2, uvicorn | Swagger UI безкоштовно |
| БД | PostgreSQL 16, `asyncpg`, ручний SQL, нумеровані міграції | один день, без ORM |
| Читання фото | Gemini (Google AI Studio, free tier), REST через `httpx` | читає зображення, JSON-режим, без картки |
| Зображення | Pillow | EXIF, resize, хеш; генератор синтетичних етикеток |
| Контейнери | Docker, Docker Compose | обов'язково |
| Тести | pytest, `FakeVision`, ізольована мережа, окрема тестова БД | без мережі і без живого LLM |
| CI | GitHub Actions: ruff + pytest, docker build | 15 хвилин, скопійовано з `pet` |

**Ризик №1 — квота Gemini.** Google більше не публікує таблицю безкоштовних лімітів; за
звітами з кінця 2025 р. для частини моделей ліміт падав до ~20 запитів на день. Тому в B0
дивимось реальні RPM/RPD свого проєкту в AI Studio і під них рахуємо eval (один виклик на
кейс; ~75 кейсів на повний живий прогін). Кеш екстракцій робить повторні заміри
безкоштовними. Запасний vision-провайдер — лише якщо в B0 знайдено безкоштовний без картки
(у `pet` Llama на Groq уже недоступна, а `gpt-oss` не бачить зображень).

## 5. Логіка крок за кроком

### Крок 1. Прийом фото
Фото з телефона часто «лежать на боці» (поворот записаний в EXIF) і завеликі. Вирівнюємо і
зменшуємо до 2048 px. `sha256` — відбиток фото: потрібен для кешу і аудиту. У БД
зберігаються **байти** підготовленого фото — саме те, що бачила модель.

### Крок 2. Екстракція — єдине місце, де працює AI
Gemini отримує всі фото й інструкцію: «перепиши, що бачиш, у таку структуру; нічого не
оцінюй; не перекладай і не виправляй; нечитабельне — null». Результат — `LabelExtraction`:

```json
{
  "photos": [{"index": 0, "side": "front", "quality": "ok"},
             {"index": 1, "side": "back", "quality": "ok"}],
  "emphasis_visible": true,
  "ingredients_marked": {"photo_index": 1,
    "text": "борошно **пшеничне**, цукор, сухе **молоко**, олія соняшникова, **ЯЙЦЕ**"},
  "may_contain_text": "Може містити горіхи та кунжут",
  "nutrition": {"photo_index": 1, "per": "100g",
    "energy": "1760 кДж / 420 ккал", "fat": "18", "saturates": "9", "carbs": "58",
    "sugars": "3,1", "fibre": "2", "protein": "6", "salt": "<0,1"},
  "other_text": [{"photo_index": 0, "text": "БЕЗ ЦУКРУ"},
                 {"photo_index": 0, "text": "Джерело білка"},
                 {"photo_index": 0, "text": "Печиво вівсяне"}]
}
```

`emphasis_visible` — чи видно на фото різницю шрифтів у складі взагалі. Якщо ні (розмито,
відблиск) — `ALG-EMPH` не вгадує, а дає `needs_review`.

**Кеш**: ключ = sha256 усіх фото + `PROMPT_VERSION` + модель. Повторна перевірка тих самих
фото (зокрема в eval) не витрачає ліміт.

**Найслабше місце системи** — чи бачить модель жирний шрифт. Тому точність виділення
міряємо окремою метрикою, а перша 10-хвилинна проба на справжньому фото — ще в B1,
до написання правил: якщо модель жирного не бачить, це змінює схему, і краще знати це до B2.

### Крок 3. Розбір — код
- `parse_amount("<0,5")` → `{value: 0.5, qualifier: "lt"}`; `"3,1"` → `3.1`; `"сліди"` →
  `{value: 0, qualifier: "trace"}`; `"1760 кДж / 420 ккал"` → `kj`, `kcal`. Нерозбірне →
  `null`.
- Розбір `ingredients_marked`: спани `**…**`, слова ВЕЛИКИМИ, вкладені дужки
  («шоколад (цукор, какао-масло, **соєвий** лецитин)»).

### Крок 4. Правила — серце сервісу

| Група | Що перевіряє | Приклад порушення |
|---|---|---|
| **Загальні** | якість фото, є склад і таблиця, є фронт, таблиця на 100 г | розмите фото → `needs_review` |
| **Алергени** | кожна згадка алергену виділена; з рецептурою — усі алергени з неї є на етикетці | «пшеничне борошно» без жирного |
| **Твердження** | напис відповідає порогу з наказу МОЗ № 1145 | «без цукру», а цукрів 3.1 г (поріг 0.5 г) |
| **Узгодженість** | енергія ≈ 4·вуглеводи + 4·білок + 9·жир; цукри ≤ вуглеводи | заявлено 420 ккал, а з макро виходить 310 |

Алергени: `ALG-EMPH`, `ALG-SPEC-MISSING`, `ALG-SPEC-EXTRA`, `ALG-MAY-CONTAIN` (деталі —
`CLAUDE.md`). Словник — основи українських і англійських форм 14 категорій **плюс список
виключень**: кокосове молоко, мускатний горіх, гречка, какао-масло, соняшникова олія — не
алергени з переліку. Без виключень сервіс тривожив би на кожному шоколаді.

Твердження (на 100 г / 100 мл): `sugar_free` ≤ 0.5 г; `low_sugar` ≤ 5 / 2.5 г;
`no_added_sugar` — без цукрів і підсолоджувальних продуктів у складі, а якщо цукри > 0 —
напис «містить природні цукри»; `protein_source` ≥ 12 % енергії; `protein_high` ≥ 20 %;
`fat_low` ≤ 3 / 1.5 г; `fat_free` ≤ 0.5 г; `satfat_low`; `fibre_source` ≥ 3 г/100 г або
1.5 г/100 ккал; `fibre_high` 6 / 3; `salt_low` ≤ 0.3 г; `salt_very_low` ≤ 0.1 г;
`energy_low` ≤ 40 / 20 ккал.

Приклад рахунку «джерело білка»: білок 6 г × 4 ккал = 24 ккал з 420 = 5.7 % енергії;
поріг 12 % → `violation`, `evidence = {fragment: "Джерело білка", values: {protein: 6,
kcal: 420, protein_energy_pct: 5.7}, threshold: 12}`. Рахує код, не модель.

**Подвійна роль перевірки енергії**: вона ловить і помилку на етикетці, і помилку
читання фото моделлю (контрольна сума). Якщо числа не сходяться, сервіс не вгадує, хто
помилився, — `needs_review`.

### Крок 5. Вердикт і п'ять статусів
- `pass` — перевірено, відповідає;
- `violation` — точно порушення;
- `needs_review` — сервіс бачив, але не впевнений: розмите фото, не видно шрифту,
  порівняльне твердження, числа не сходяться;
- `not_checked` — бракує вхідних даних: немає рецептури (повнота алергенів), немає фото
  фронту (твердження);
- `not_applicable` — правило не стосується продукту.

Загальний вердикт: є `violation` → **fail**; інакше є `needs_review` → **needs_review**;
інакше є `not_checked` → **incomplete** (з переліком, що не перевірено); інакше **pass**.

Чому окремий `not_checked`: якби відсутність рецептури давала `needs_review`, кожна
перевірка без рецептури мала б вердикт `needs_review`, і метрика «показали людині» стала б
100 % для будь-якого порушення — тобто безглуздою. «Сумнів» і «не дали даних» — різні
речі для технолога і для числа довіри.

### Крок 6. Аудит
Для кожної перевірки в БД: байти фото, сира відповідь моделі, екстракція, findings,
версії правил і промпта, модель, токени, тривалість. Якщо партію відкличуть — можна точно
сказати, чи модель неправильно прочитала, чи правило спрацювало не так; а оскільки правила
детерміновані, будь-яку стару перевірку можна перерахувати новими правилами без LLM.

### Роль рецептури

| | Без рецептури | З рецептурою |
|---|---|---|
| Алергени виділені? | ✅ | ✅ |
| Усі алергени продукту є на етикетці? | `not_checked` | ✅ звіряє з рецептурою |
| Твердження і пороги | ✅ | ✅ (`form` з рецептури) |
| Нутрієнти етикетки = рецептурі? | — | ✅ у межах допусків |

## 6. API

- `POST /checks` — `multipart/form-data`: `images` (1–4 файли JPEG/PNG/WebP, ≤ 10 МБ),
  `spec` (необов'язково, JSON `ProductSpec`).
- `GET /checks/{id}` — збережена перевірка.
- `GET /rules` — усі правила з посиланнями на закон.
- `GET /health` — стан сервісу, БД і провайдера.

Відповідь: `{check_id, verdict, summary, findings[], extraction, model, rules_version,
prompt_version, duration_ms}`; `finding = {rule_id, target, status, message, evidence,
legal_ref}`. `evidence` містить номер фото і дослівний фрагмент — технолог має за 5 секунд
знайти місце на упаковці. Помилки: `{"error": {"code": "...", "message": "..."}}`.

## 7. Число довіри — як отримуємо

```
eval/generate.py ──► ~60 синтетичних етикеток з ВІДОМИМИ порушеннями
                     (чисті + розмиті / повернуті / стиснуті), dev-пул і test-пул
                     формулювань окремо
eval/real/       ──► 10–15 справжніх українських упаковок (телефон / Open Food Facts),
                     розмічені вручну; + напівсинтетика: справжнє фото + рецептура з
                     навмисною розбіжністю
                     │
          ┌──────────┴──────────┐
         dev                   test
   (налаштовуємо тут)   (міряємо ОДИН раз у кінці)
                     │
eval/run.py     ──► run_check() — той самий код, що й POST /checks
eval/metrics.py ──► safe recall [Wilson 95 %] + навантаження на людину + базова лінія
```

**Як зараховуємо**: порушення з `truth.json` — пара `{rule_id, target}`. Воно «знайдене»,
лише якщо серед findings є той самий `rule_id` + `target` зі статусом `violation` або
`needs_review`. Загальний вердикт для зарахування **не** використовується — інакше
`needs_review` через розмите фото «зловив» би порушення «без цукру», якого сервіс не бачив.

**Головне число — пара**:
- **safe recall** — частка справжніх порушень, які сервіс показав технологу, з 95 %
  інтервалом Вілсона: «знайшов 28 з 30 — 93 % [79–98 %]»;
- **навантаження** — частка чистих етикеток, які все одно пішли людині.

Поруч — **базова лінія** «все → needs_review»: safe recall 100 %, навантаження 100 %. Без
неї 100 % safe recall нічого не означає; з нею видно, скільки роботи сервіс знімає.

Також: strict recall (лише `violation`); хибні тривоги (`violation` на чистих); розбивка за
типом порушення, якістю фото, синтетика/справжні.

Дві стадії окремо — щоб бачити, де помилки:
- **точність читання**: числа після розбору, виділення алергенів (окремо: чи ловить «не
  виділено»), знайдені твердження;
- **точність правил на ідеальних даних** — `truth.extraction` → правила → має бути 100 %.
  Це pytest-тест без LLM: якщо не 100 %, баг у коді, а не в моделі.

**Чесність виміру**:
- усе налаштовуємо лише на `dev`; фінальне число — з `test`, один раз;
- **окремі пули формулювань** для dev і test: генератор і словник пише той самий Claude,
  тож без цього синтетика містила б лише слова зі словника, і recall був би штучно високим.
  У пулах є форми, яких немає в словнику («сухе знежирене молоко», «лактоза», «сироватковий
  білок», «яєчний меланж»), і пастки («кокосове молоко», «мускатний горіх»);
- справжні фото — лише в `test`; без порушень вони міряють хибні тривоги й читання, а
  напівсинтетика з підміненою рецептурою додає на них справжні порушення;
- синтетика позначається як синтетика; межі виміру — у README.

Каталог навмисних порушень у синтетиці: алерген не виділений; «без цукру» при цукрах >
0.5 г; «джерело білка» при < 12 % енергії; «низький вміст жиру» понад поріг; «без доданого
цукру» з медом/сиропом у складі; енергія не сходиться з макро; алерген з рецептури
відсутній на етикетці; + чисті етикетки, зокрема з «<0,5» цукрів і «без цукру» (пастка для
розбору чисел).

## 10. Чим свідомо жертвуємо

- Фронтенд — лише Swagger UI.
- Твердження про користь для здоров'я, порівняльні й нерегульовані — `needs_review`, без
  автоматичного вердикту.
- Набір для оцінки здебільшого синтетичний (синтетика легша за реальні фото) — прямо в
  README; справжніх фото лише 10–15, інтервал широкий.
- Одна модель, одне читання. Подвійне читання (дві екстракції, розбіжність →
  `needs_review`) подвоїло б витрату ліміту — винесено в «що далі».
- Запасний vision-провайдер — лише якщо знайдеться безкоштовний без картки.
- Нутрієнтні допуски етикетки vs рецептури — стартові (±20 % / ±2 г), не повна настанова
  ЄС щодо допусків.
- Синхронний `POST /checks` (5–20 с) — без черги задач.

## 11. Що далі (поза 8 годинами)

- Більше справжніх фото і розмітка технологами → вужчий інтервал числа довіри.
- Подвійне читання / друга модель для чисел і виділення; розбіжність → `needs_review`.
- Твердження про користь для здоров'я (реєстр дозволених тверджень).
- Інші обов'язкові елементи етикетки: назва, маса нетто, термін придатності, умови
  зберігання, виробник, мінімальний розмір шрифту.
- Інтеграція з системою рецептур (PLM), щоб рецептура підтягувалась автоматично.
- Інтерфейс для технолога з підсвіткою проблемних місць на фото.
- Черга задач для перевірок і повторна перевірка старих етикеток новими правилами.
